# Qwen3.5 LoRA 4096/8192-token path study (2026-10-01 JST)

## Decision

The host-checkpoint fallback needs different buffer lifetimes at the two tested lengths. At 8192 tokens, direct GPU buffer handoff saves host uploads and reduced one-update time from 793.132 to 777.342 seconds (1.99%). At 4096 tokens, that same handoff increased time from 293.671 to 330.643 seconds (12.59%). A separate forward copy-and-reuse path ran at 290.625 and 292.124 seconds against a 292.366-second same-binary control. This difference is too small and inconsistent to establish a speed gain.

Fusing causal attention score and softmax by query row is the first tested improvement that applies at **both** lengths: 4096 dropped from 292.366 to 281.285 seconds (3.79%), and 8192 with direct handoff dropped from 777.342 to 747.878 seconds (3.79%). Loss and gradient norm matched exactly at both lengths. Fusing the output stage as well yielded 279.596 seconds at 4096, only another 0.60%; it is not a priority. All new modes remain opt-in while longer runs and the long-context memory design are evaluated.

A same-binary 4096 confirmation was 291.945 seconds without row fusion and 281.431 seconds with it (3.60% reduction). The full exploratory 8192 combination (handoff, streamed tile512, row fusion, rolling IQ2 transpose) was 732.245 seconds versus the original 793.132-second control (7.68% reduction). It matched loss and gradient norm exactly, but the 8192 combined result is still one update per variant across different binary snapshots, not an epoch throughput claim.

The earlier packed causal attention and GPU gradient retention remain the 4096 baseline. Their paired two-sample improvement over the older path was 2.20%; see `lora-speed-4096-2026-09-30-final.md`.

## Fixed setup and scope

Qwen3.8-27B-Uncensored-noMTP-IQ2_M.gguf, QA80 record 77 cycled to exactly 4096 or 8192 tokens, devices Arc B580 0/1, rank 8, alpha 16, all LoRA targets, one fresh update per trial. The benchmark uses FP16/XMX IQ2 forward, packed attention, GPU gradient retention, 1024 MiB per-device IQ2 projection cache, 2048 MiB buffer pool, transpose8, and disabled kernel timing. The existing CLI default IQ2 precision is **exact**, so these timings do not measure its speed. Reports preserve the model/data hashes, full token IDs, options, binary hashes, loss, gradient norm and device counters. Original data and production checkpoints were not changed.

One-update synthetic timing is exploratory. It does not establish full-epoch throughput or heldout response quality. Backend peak allocation is cumulative live OpenCL allocation, not measured physical VRAM residency.

Every accepted 4096 trial reported loss 1.285513789891044 and gradient norm 0.2326987973948727. Every completed 8192 trial reported loss 0.6507614145002314 and gradient norm 0.4979216137231339. The pair validator required identical model/data hashes, token IDs, LoRA setup and device layout, and explicitly approved only each tested execution-option difference. Comparison JSON is under `benchmark-results/lora-speed-8192-20261001/`.

The 4096 online-attention experiment is excluded from the parity statement: loss was 1.28448202852306 and gradient norm 0.240590505423007. Its small-shape GPU tests passed within 2e-4, but long-sequence full-model behavior and speed both failed the adoption criterion. The experimental source was removed; the frozen benchmark binary and result JSON preserve the evidence.

Direct handoff approximately halved host-to-device bytes at both lengths. At 4096, forward retention itself caused a large slowdown despite less transfer; copying into the dead input buffer avoids retaining the output tape allocation, and small-model one/two-device parity tests passed, but its speed effect was negligible on repeat. At 8192, direct handoff and fused score/softmax left the ~19.9 GB/device backend peak unchanged. The original streamed attention reduced that peak to ~14.9 GB/device but recomputation outweighed the saving. Streamed plus row-fused attention kept the ~14.9 GB/device backend peak while cutting the one-step time from 747.878 to 739.824 seconds. IQ2 rolling transpose then reduced 739.824 to 732.245 seconds without changing that peak. Both ~1% increments are exploratory; the larger benefit of streaming is memory headroom. These observations do not prove a physical VRAM paging mechanism.

## Implementation and use

`TrainingHostCheckpointBufferHandoff` (CLI `hostCheckpointBufferHandoff`) enables direct forward/backward buffer ownership transfer. `TrainingHostCheckpointForwardCopyHandoff` (CLI `hostCheckpointForwardCopyHandoff`) copies each forward layer output into a reusable GPU input buffer and returns the output allocation to the pool. `TrainingFusedAttentionRows` (CLI `fusedAttentionRows`) combines causal score and softmax kernels. `TrainingFusedAttentionOutput` combines their output stage too, with negligible additional measured speed. All are off by default. Enable only the matching measured mode for a fresh benchmark or training configuration; setting both handoff modes combines unmeasured behavior. `TrainingStreamedAttentionTileRows=512` bounds attention score workspace: it was slower without row fusion but useful with it at 8192.

For a **new** 4096-token run, the measured setting is `fusedAttentionRows: true` with direct handoff and streamed tiles left off. For a **new** 8192-token run, the measured lower-memory setting is `fusedAttentionRows: true`, `streamedAttentionTileRows: 512`, and `hostCheckpointBufferHandoff: true`. The optional `iq2RollingTranspose: true` adds about 1% in one full 8192 update and remains off by default. Preserve a resumed run's saved configuration and numerical path.

The existing quantized weights already reside on both Arc devices (about 4.69/4.77 GiB of encoded weights per lane), so preloading more layers cannot remove weight transfer from these runs. An experimental bounded hybrid GPU/host checkpoint option passed 1/2-device small-model parity, but 4096 backend peak is effectively at the Arc allocator's 90% budget and 8192 exceeds it. A full-model speed benefit is unverified; this option stays off.

The relevant source is `NNtrain.Core/Modules/Qwen35QuantizedModel.Lora.cs`, `Qwen35TrainingTape.cs`, `Qwen35TrainingAttention.cs`, `Qwen35ExecutionOptions.cs`, the CLI configuration and option mapping, and the optional streamed OpenCL kernel. The benchmark harness is `tools/compare_lora_speed.py` plus the frozen probe binaries and JSON reports. No production LoRA training was started for this study.
