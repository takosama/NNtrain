# DPO throughput and memory — 2026-09-10

## Applied

- Completion-only LM head: do not materialize vocabulary logits for prompt/padding; hidden forward still includes the whole causal sequence.
- Frozen base linear backward: retain dX, omit dW/db allocations and computation. Embedding/LayerNorm base gradients remain.
- Pipeline gradient accumulation: train each ready microbatch while subsequent pairs generate. Normalize partial epoch tails by actual pair count before clipping.
- Resume accepts queue/slot changes and microbatch repartitioning with identical effective batch; queued pairs are not discarded when capacity shrinks.
- Avoid duplicate checkpoint writes at the same committed step.
- Config: batch **2**, accumulation **8** (effective **16**), generation slots **4** on `[0,1,0,1]`, queue **8**. LR, beta, context, sampling limits and sample interval were not changed.

## Synchronized training benchmark

Windows, RTX 3070 Ti GPU 0, Release, loaded DRN base (65,418,476 base parameters), width 512, hidden 1536, 32 layers, key/value 32, vocabulary 11500. LoRA rank 8 / alpha 16, mix16_32, AdamW LR 0.0001, clip 1, DPO beta 0.1. Fixed seeded synthetic pairs, batch 2 (4 chosen/rejected rows), sequence exactly 1024, no generation workers. Two warmup + five measured updates; an extra synchronized operator profile is excluded.

| Metric | Legacy | Optimized |
| --- | ---: | ---: |
| Update median | 1027.7 ms | 984.3 ms |
| Lane allocated after backward (includes cache) | 931.7 MiB | 704.9 MiB |
| Lane allocated at forward boundary, warm | 4165.0 MiB | 3805.5 MiB |
| Whole-board used at forward boundary, warm | 5354.5 MiB | ~4934.5 MiB |

Training-only time reduced **4.2%**, warm forward-boundary board memory reduced approximately **420 MiB**. After-backward allocator reduction is **24.3%**, not a claim that total training VRAM falls 24.3%. Boundary readings are not continuous peak measurements. BF16 GEMM grouping and nondeterministic kernels mean update trajectories are not bitwise-identical. Synthetic repeated pairs are a throughput test, not a convergence benchmark.

Batch 1: median 589.8 ms/microbatch, ~1179.6 ms per two pairs, worse throughput than batch 2. Batch 4 attempt failed with OOM after the first update; small integration tests were also launched during that attempt, so it is not an isolated capacity limit measurement. Batch 4 was not adopted.

Raw records: `benchmark-results/dpo-final-legacy-b2-t1024.json`, `dpo-final-b2-t1024.json`, `dpo-after-b1-t1024.json`. Legacy can be reproduced with the probe's `legacy` argument; no production checkpoint is written.

## Generation + training scheduler comparison

Same base, same first 20 FineWeb documents (copied to benchmark-only JSONL), context cap **128**, batch 2, accumulation **2**, five updates, fresh adapters, no periodic samples, final checkpoint. Both GPUs. All rows below already use optimized scoring and pipelined accumulation. These are **single short runs**, including model loading/final save; not the production context-1024/accumulation-8 throughput guarantee. Async completion order, snapshot age and EOS termination can differ.

| Generation slots | Queue capacity | 20-pair wall time |
| ---: | ---: | ---: |
| 2 | 2 | 71.154 s |
| 2 | 8 | 53.542 s |
| 4 | 8 | 38.372 s |

Observed reduction from first to last: **46.1%**. Generation waiting dominates (roughly 90% in the small-queue trial); optimizing training arithmetic alone cannot produce this end-to-end gain. Additional slots add private generator models, a memory/throughput tradeoff rather than free acceleration.

Logs/configs/isolated adapters: `benchmark-results/dpo-pipeline-q2/`, `dpo-pipeline-q8/`, `dpo-pipeline-q8-s4/`.
