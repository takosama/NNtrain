# Parakeet 高速化・停止後確定の検証（2026-10-06）

公開済み main の基準は `c1b53d23d5bf750659595d71ceb45bbc7cf6f505` です。この文書の最終結果は未コミットのローカル高速化差分を含み、公開済み実装の性能とは区別します。重みの追加取得、実マイク録音、学習・実 LLM の起動は行っていません。

## 測定条件

Ryzen 7 5700X、RAM 64 GB、Intel Arc B580 12 GB の単一 ASR GPU を使用しました。承認済みの公開 FLEURS 日本語 PCM16 3 本と、公式 NeMo の FP16 丸め済み CPU 参照を比較しました。本番認識は独自 C# / OpenCL で、Python は公式数値参照だけです。GPU テストは ASR 専用で順番に実行し、既存プロセスの終了や重複起動は行っていません。

全ファイル認識時間はチェックポイント読み込み・GPU 重みアップロードを除外します。最終 encoder trace の出力は測定に含みます。メモリは Windows のプロセス別 GPU カウンターを周期観測した値で、瞬間的な未観測ピークを保証しません。バックエンドの割り当てバイト数だけを総 VRAM とみなしていません。

## 原因と最終実装

11.1 秒の入力に対する基準プロファイルは 9.10 秒で、そのうち CPU global attention は 6.221 秒でした。268 回の密行列処理合計は 0.785 秒で、主な原因は CPU attention のスカラー処理でした。

第一段階は CPU attention の SIMD 化、最大 4 worker の独立行処理、発話内での相対位置の共有、畳み込みの小さな係数配列、LayerNorm / sigmoid の処理整理です。重みは FP16 のままで、モデル全体の FP32 コピーは作りません。

最終段階では Arc 経路の Q/K/V・相対位置投影、全体 attention の score / softmax / context / 出力投影を GPU 内で連結しました。FFN も投影→SiLU→投影を GPU 内で完結させ、ホストとの往復を減らします。前処理・畳み込み・正規化などは CPU 経路を残し、CPU 選択時は SIMD 実装を使います。全体 prefix を毎回認識する構造は維持し、異なる prefix 間の encoder キャッシュを流用していません。

3 本とも以前のネイティブ認識文と完全一致し、公式参照の正規化認識結果を維持しました。公式 FP16 丸め参照との全 encoder 値の最大 / 平均絶対誤差は、それぞれ `3.09944e-6 / 2.09161e-7`、`1.21593e-5 / 3.82772e-7`、`5.48363e-6 / 3.32410e-7` です。FP32 の並列 reduction と指数関数の丸め差があるため、ビット一致とは言いません。3 本の一致は一般的な認識精度を保証しません。

公式 4-thread CPU 推論は約 0.709 / 1.315 / 0.530 秒で、この比較条件では最終の独自実装より高速です。Arc 使用だけで公式実装を上回ったという主張はしません。

最終の 3 本を通した専用 GPU メモリ観測ピークは `1,349,222,400` バイトでした。実時間供給 GUI テストでは専用 `1,354,067,968` バイト、共有 `12,836,864` バイトが別々の観測ピークです。ASR 単体の専用 VRAM は 2 GB 目標を満たしました。LLM との合算、同時負荷は未測定です。

## 途中表示・停止・確定

最初の途中認識は約 1 秒の入力から開始します。後続は最低 2 秒の追加入力を待ち、処理時間の 1.5 倍、上限 8 秒の入力間隔へ調整します。認識は全 prefix の再計算で、途中結果は書き換わります。最大 30 秒 / 発話の制限は維持します。

録音 consumer は最大 17 個の取得済み chunk をまとめ、全サンプルと末尾を保持します。録音キューは有限です。停止は任意の進行中 preview だけを中断し、キューを取り込んで完全な最終認識を実施します。キャンセルは発話自体を破棄します。完全に同じ sample count の prefix を既に処理済みの場合のみ、最終結果を再利用できます。

| 実時間供給 22.86 秒 | 第一段階 | 最終 |
| --- | ---: | ---: |
| 最初の文字表示 | 1.590 秒 | 1.510 秒 |
| 停止前の変更表示回数 | 5 | 7 |
| 停止から確定 | 6.078 秒 | 2.963 秒 |
| 最大 queue / 終了時 queue | 12 / 0 | 7 / 0 |
| 最大 sampled processing lag | 3.994 秒 | 2.662 秒 |
| 最大 dispatcher tick gap | 39.7 ms（録音中） | 37.8 ms（確定まで） |

最終テストでは `353280` samples の preview が停止時に中断され、`365760` samples の最終認識が 1 回だけ行われました。末尾の `12480` samples（0.78 秒）は旧 preview には含まれません。最後に完了した preview も `291840` samples なので、結果を単に確定扱いして最終認識を省くと末尾が失われます。最終認識自体は約 2.960 秒で、残る確定遅延の中心は完全 prefix の計算です。最新 GUI 修正前の GPU 融合試験も停止後 2.986 秒で、再測定と近い値でした。

GUI は最終文を Dispatcher 上の入力欄へ反映する Task を待ってから編集・送信を再開します。反映前に編集可能になる競合を回帰テストで防ぎます。発話の世代、再開時の新規 stream、停止連打、Cancel による下書き復元の制御を維持しています。

最終 GPU 融合と GUI 最終反映の待機を含む再検証では、11.1 秒の最初の表示 1.494 秒、停止後確定 1.501 秒、再開後の停止後確定 1.459 秒でした。最大 queue は 3、正常終了時は 0。3.84 秒時点のキャンセルは 39.7 ms で終了し、下書きを復元して新しい発話を開始できました。キャンセルされた発話の未処理 chunk 1 個は破棄され、再開へ持ち越しません。確定までの dispatcher tick gap は通常 43.6 ms、再開 35.4 ms でした。二重開始の拒否と認識文の一致も通過しました。

## テストと証拠

ローカルの `benchmark-results/asr-20261006` に保存しています。生ログ・重み・音声は公開物に含めません。

- `parakeet-performance-baseline.json`: 原因のプロファイル。

- `parakeet-performance-arc-fused-three.json`: 最終ファイル認識。
- `parakeet-arc-fused-official-comparison.json`: 公式 encoder 全値との誤差。
- `parakeet-realtime-arc-fused-longest.json`: 最終 GPU 融合の実時間供給、preview / final の回数・sample count・メモリ。
- `asr-readme-final.trx`: 最新 CPU ASR 34 件。
- `asr-readme-arc-final.trx`: 両 B580 の encoder / 密行列比較を含む ASR GPU 3 件。
- `parakeet-realtime-readme-final.json`: 最新 GUI 反映の待機を含む 11.1 秒・キャンセル・再開。
- `parakeet-realtime-readme-longest-final.json`: 最新 GUI 反映の待機を含む 22.86 秒の実時間供給。
- `parakeet-composer-readme-final.json`: 実 ASR → 編集 → 既存 Send の模擬 HTTP 接続。11.1 秒の非実時間入力で認識処理 2.317 秒、編集文と送信文は完全一致。ロードは別計測で 16.280 秒。

GUI / CLI Debug ビルドは警告・エラー 0。Core CPU の広い回帰範囲は 1,502 件通過、109 件 skip（GPU 利用クラスと opt-in profiler を除外）。オフライン WPF 状態検証は最終反映の順序を含む 11 件です。通常の Gui.Tests restore には権限問題が残るため、既存 SDK と既存依存物で検証し、制限を迂回していません。

ルート README、GUI README、API ガイドのローカルリンク 35 件を実ファイルと照合しました。生成・学習・起動オプションは各 C# パーサーと照合し、GGUF / LoRA / データ準備の例は存在しない入力を指定して実際のパーサーが入力検証まで到達することを確認しました（生成 / LoRA は終了 2、準備は終了 1）。実モデルの起動や学習を説明確認のために実行していません。

実 ASR の確定文を編集し、既存 Send で正確な編集文を送る検証は模擬ローカル HTTP を使用します。これは実 LLM による回答生成とは区別します。実マイク、30 秒持続、他の話者・雑音、LLM 同時負荷、長時間の複数発話は未検証です。TDT と encoder のキャッシュ付き Parakeet ストリーミングは残作業です。
