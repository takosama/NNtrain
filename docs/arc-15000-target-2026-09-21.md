# Arc B580: 15,000 tokens/sを目標にした実測最適化

前回の [全体timelineと融合GEMMの報告](arc-throughput-fusion-2026-09-21.md) を起点に、
最大区間のAttention backward、GEMMタイル、weight packing、microbatchを実装・比較した。
最終値は **11,073.4 tokens/s、23.673秒/update**。同一binaryの再測定基準から **3.99%向上**。
**15,000 tokens/sはまだ達成していない。** 数値精度を落とした経路で達成扱いにしていない。

## 固定条件

- Windows、.NET 10 Release、Intel Arc B580 12 GB、driver 32.0.101.9030。
- `training.transformer.json`: 32層、width512、hidden1536、16 heads/D32、語彙11,500、90,507,500 parameters。
- sequence1024、microbatch16 × accumulation16、実効batch256、262,144 tokens/update。
- `mix8_32` block32。BFP8保存、BF16 XMX operand、FP32累積・勾配・master weight。
- Muon固定NS5、LR0.001、補助AdamW LR0.0003、weight decay0.01、dropout0.1、seed1234。
- JSON SHA256: `D52B38CE5D91EF53A1643D8E7061D0E974872BA6D1DDD69C5047DDB10B0C9E39`。今回はJSONを変更していない。
- CLIのmodel/optimizer factoryで構築する固定seed・full-length合成tokenの訓練ベンチ。
  loss/backward/clip/optimizerを含み、FineWeb I/O、tokenizer、checkpoint、HTML、生成、schedulerは含めない。
  有限gradient検査とtrace書き出しは計測外。実データend-to-endや長期収束の数値ではない。
- GPU仕事は直列。全体artifactは実効shape、options、binary hash、各updateの内訳を保存する。

## 採用した変更

### DKVのSLMアクセスをcoalesced block readに変更

`attention_dkv_register_query.cl` の `attention_dkv_block_slm_causal/dense`。
K32/Q32、SG16、workgroup16×16、Q0/Q16/dY0/dY16をSLM上で連続配置し、
`intel_sub_group_block_read4`で読み出す。P/dSもペアで保持する。
加算順、FP32 FMA、初期gradient、causal開始位置は変更しない。

単体測定 `arc-15k-dkv-blockslm-final-20260921.json`:

| D32/T1024 | 従来GPU ms | 採用GPU ms |
|---|---:|---:|
| causal K32/Q32 | 0.1084 | 0.0829 |
| dense（従来K64/Q32） | 0.2016 | 0.1583 |

全体訓練中のDKVは約3,710.8→2,750.0 ms/update。約960 ms短縮という単体からの予測と整合する。
`BlockIoAttention`を既定有効にした。XMX/SG16/local-block-IO、D32、Tの64倍数という条件付きで、
それ以外・明示的な別DKV行数・無効設定では従来Arc経路を使用する。

### 小microbatchでも広い融合GEMMタイルを使用

既存16×64のBFP8 epilogueをM≥8192からM≥4096にも適用。
N≥512かつ64の倍数などの制限は維持する。B16本番には影響せず、B4等の経路を改善する。
M4096/N1536/K512は16×32の0.3285→16×64の0.2868 ms、
M4096/N512/K1536は0.2305→0.1821 ms。packed payload/全scaleをbit比較した。
forward、2回累積gradient、M4099とK79のtailも追加テストで合格した。

## 不採用の候補も実装・計測した

以下の数値は**単体kernel時間とupdate全体時間を混ぜていない**。
試作kernelsは `ExperimentalOptimizationKernels` または別programに隔離し、通常のdispatchには採用しない。

| 候補 | 実測結果と判断 | artifact (`benchmark-results/`) |
|---|---|---|
| DKVでQ/dYをregister保持しshuffle | 0.120～0.163 ms、旧0.109 msより遅い。大タイルはspillも発生 | `arc-15k-dkv-rq-20260921.json` |
| DKV block-IOのK/Qタイル交換 | K32/Q32が最良。K64/K128、Q16等は不採用 | `arc-15k-dkv-blockslm-tiles-20260921.json` |
| softmaxのexact subgroup reduction | 加算treeを維持してbit一致するが、T1024 causalで0.0718→0.0842 ms等、悪化 | `arc-15k-exact-reduction-20260921.json`, `arc-15k-exact-reduction-sg32-20260921.json` |
| GEMM 32×64/16×128、workgroup4/8 | 128GRFで3,840/7,296 B spill。256GRFでspillを消してもoccupancy低下で遅い | `arc-15k-epilogue-expanded-20260921.json`, `arc-15k-epilogue-grf256-20260921.json` |
| PV/dQ vector+SLM block-IO | bit一致後も約0.075 ms、既存0.071～0.072 msより遅い | `arc-15k-pvdq-blockslm-fixed-20260921.json` |
| dP block-IO | bit一致、0.0532→0.0576 msで悪化 | `arc-15k-dp-blockslm-20260921.json` |
| DKVをquery分割し2段reduction | split2のGPU0.0808→0.0766 msだが、追加launchを含むwall0.1043→0.1076 msで悪化。split4も悪化 | `arc-15k-dkv-split-20260921.json` |
| dP+dSをregister融合、現行4-head tile | wall0.0844→0.1177 ms。T1/31/65/137/1024、causal0/1/2でbit一致するが不採用 | `arc-15k-dp-ds-count4-20260921.json` |
| weight panelをmicrobatch間cache | 11,069.9 tokens/s。cacheなし11,078.1に劣り、peak+320 MiB、毎update112.52 MiBのnative確保/解放が再発 | `arc-15k-dkv-cache-b16-20260921.json` |
| microbatch4 × accumulation64、cache併用 | 10,787.1 tokens/s、24,301.65 ms/update。16×16を維持 | `arc-15k-b4-a64-20260921.json` |
| Attention workspaceを64→32 MiB | 10,964.6 tokens/s、23,908.11 ms/update。forwardが遅くなり不採用 | `arc-15k-workspace32-20260921.json` |

PV/dQ試作の初版はlocal float4の成分storeが競合し検査に失敗した。
scalar SLM storeへ直して全配列bit一致を確認した後に比較し、速度が劣るため不採用にした。
DKV splitはFP32だが和の結合順が変わるため試作専用の絶対差1e-6検査であり、
採用経路のbit一致試験や既存テスト許容誤差とは別物。通常の学習には導入していない。

weight panel cacheはtensor所有・lane予算内・最大2レイアウトで実装した。
host mutation、optimizer update、precision変換の前に無効化し、解放/予約回収も検査した。
全体性能が改善しなかったため `MatrixPanelCacheMiB=0` を維持する。
最終defaultではcacheに伴うVRAM増加やnative確保/解放を発生させない。

## 最終測定と検証

| 比較 | warmup / 測定updates | p50 ms/update | tokens/s | peak割当 MiB |
|---|---:|---:|---:|---:|
| 開始時の凍結基準 | 2 / 4 | 24,627.35 | 10,644.4 | 5,365.87 |
| 今回と同一binary、BlockIo OFF再測定 | 2 / 2 | 24,617.35 | 10,648.7 | 5,365.87 |
| 最終default、排他的timeline ON | 2 / 4 | **23,673.33** | **11,073.4** | **5,365.87** |

OFFは `arc-15k-baseline-recheck-20260921.json`、ONは
`arc-15k-final-timeline-20260921.json`。Core/Arc/Benchmarksのbinary SHA256が一致することも確認した。
両方とも詳細profile有効。ONだけはさらに排他的timelineを記録し、profilerを外した側を
高速化結果として比較していない。既存より3.83%短時間、tokens/sで3.99%向上。
15,000 tokens/sに必要な時間は17,476.27 ms/update。**残り6,197.06 ms、さらに26.18%の時間削減が必要**。

4実測updatesは23,677.4247 / 23,667.5107 / 23,734.4974 / 23,669.2351 ms。
モデル・精度・文脈長・実効batchを減らしてスループットを水増ししていない。

### 排他的wall timelineとAmdahl評価

4本の `.step-3`～`.step-6.trace.json.gz` を保存。
圧縮raw traceはローカル保持（今回分約128 MiB、過去分を含め約950 MiB）とし、
Gitには集計JSONと本レポートを収録する。raw traceは末尾のコマンドで再生成できる。
外側stopwatch合計94,748.6679 ms、明示trace窓合計94,748.5824 ms。
境界の差は合計0.0855 msであり、未計測kernelではない。
各窓のcoverage100%、device events314,106、missing/opaque uploads/GPU overlap/未帰属hostはすべて0。
clock bracket uncertaintyは0.02845～0.02890 ms。

| 排他的区間 | 平均 ms/update | wall比率 |
|---|---:|---:|
| GPU attention | 9,971.48 | 42.10% |
| GPU GEMM（融合epilogue込み） | 6,473.29 | 27.33% |
| GPU pack/decode/publication | 3,786.00 | 15.98% |
| GPU normalization/reduction | 2,278.87 | 9.62% |
| GPUその他/loss | 866.61 | 3.66% |
| GPU転送H2D/D2H/D2D | 2.13 | 0.009% |
| 計測laneのGPU idle（host/queue待ち等） | 308.77 | 1.30% |

丸め前の全区間をJSONに保存した。GPU idleのうちevent回収115.16 ms、
queue部分待ち99.98 ms、submit51.62 ms、managed backward16.02 ms。
host viewにはqueue部分待ち18,533.97 msやsubmit2,426.41 msが見えるが、大部分はGPU実行と重なる。
これをGPU kernel時間に再加算してwallの100%を超える説明はしない。
allocation-poolのhost時間37.72 msに対し、露出したGPU idleは1.61 ms。

単独最大kernelはなおDKVの2,749.92 ms/update（約11.6%）。これだけをさらに2倍にしても
全体は約1.062倍、仮にゼロにしても約12,520 tokens/s。**DKVだけでは15,000に届かない**。
Attention全体を2倍にしても他区間一定なら約14,017 tokens/sなので、次の大幅改善には
Attentionに加え、GEMM/packの同時削減が必要。今回試した大型GRF・融合・cacheは
その候補だが、現行実装では実測が悪化したため有効化しなかった。

### メモリと転送

4測定updatesすべてで **native allocation=0 bytes、native free=0 bytes**。
update境界のactive1,478.14 MiB、cache3,887.73 MiB、peak5,365.87 MiBが一定。
既存poolの再利用であり、要求バイト数やTask Managerの波形をnative確保量と混同しない。
これらはOpenCL ownerの割当集計であり、driverの物理VRAM residencyの直接測定ではない。
スクリーンショットの全変動をこの値だけで説明できたとは主張しない。

各updateのH2Dは2,097,152 bytes（token/target）、D2Hは2,636 bytes
（loss/clip/既存Muon scalar diagnostics）。weight/activation/gradientの暗黙readbackは追加なし。
初期weight upload、明示的な検査、session終了時の同期はこの定常step計測とは区別する。

## 再現

学習を停止し、既存でない出力名を指定する。

```powershell
dotnet build .\NNtrain.Benchmarks -c Release
dotnet run --project .\NNtrain.Benchmarks -c Release --no-build -- `
  --probe-arc-transformer .\training.transformer.json .\benchmark-results\arc-15k-repeat.json `
  --warmup 2 --steps 4 --timeline
```

今回の主要最適化だけを切る比較は `--block-io-attention off` を追加する。
探索用weight cacheは `--panel-cache-mib 512`、microbatch交換は
`--batch 4 --accumulation 64`。各実験は別の出力名・GPU上で直列に実行する。
