# DRN学習高速化：2026-09-06

## 結果

現在のJSONのモデル・batch・精度・optimizerを維持した2GPU比較で、
**step中央値を1,344.72 → 1,040.95 ms（22.59%短縮、1.292倍）**に改善。
CUDA allocatorの所有メモリ量は両GPUとも変更前後で同一。
この結果は訓練stepの処理速度であり、実FineWebの収束改善やloss停滞解消の主張ではない。

| 指標 | 旧版 | 新版 |
|---|---:|---:|
| step p50（各40測定点を統合） | 1,344.72 ms | 1,040.95 ms |
| step平均 | 1,342.79 ms | 1,043.47 ms |
| tokens/s（平均時間から算出） | 24,403 | 31,403 |
| GPU0 allocator所有量 | 5,684.75 MiB | 5,684.75 MiB |
| GPU0全使用量（各run測定終了時） | 7,276.5 MiB | 7,276.5 MiB |
| 各測定stepのnative allocation/free | 0 / 0 | 0 / 0 |
| 各runの新規Graph capture / replay / fallback | 0 / 20 / 0 | 0 / 20 / 0 |

旧版の各run p50: 1,333.34 / 1,348.18 ms。
新版の各run p50: 1,033.91 / 1,045.28 ms。
GPU1のallocator所有量も双方5,960,627,820 bytesで一致。
GPU1の物理VRAM使用量にはデスクトップ等の変動が含まれる。
保存・生成を含む本番全期間のVRAMピークを保証する数値ではない。

## 固定条件と比較方法

- Windows x64 / .NET10 Release / 2×RTX3070Ti (SM86)。
- 開始時の `training.forgetmemorydrn-wiki-jp.json` を別ファイルに凍結。
- DRN、48層、width512、hidden1536、K/V32、vocabulary11,500。
- batch16（GPUごと8）、context2048、accumulation1、dropout0.1、seed1234。
- mix8_32 block128。BF16 Tensor Core operands、FP32再帰状態・勾配・master・optimizer統計を維持。
- 通常Muon（momentum .95 / Nesterov / NS5毎更新）LR .001、補助AdamW LR .0003、
  beta1 .9 / beta2 .95、weight decay .01、clip1。LRは固定。
- 同じCLIモデル・optimizer factoryとCUDA Data Parallel / Graphを使用。
- 固定seedの合成token/target、全長・全target有効。データセット読込、BPE、
  scheduler進捗、checkpoint、HTML、生成は速度測定に含めない。
- 最終比較は同一managed実行ファイルでDLLだけを切替。
  **旧1 → 新1 → 新2 → 旧2**、毎回新規プロセス、10 warmup + 20 measured steps。
- 通常経路の測定後、同期を追加した診断5 stepsを実行。通常step時間とは区別する。
- 新しいbenchmark commandの通常Muon対応は両条件に共通。本番JSONは編集していない。
- 初回の3 warmup / 10 measured、およびeager演算別診断は最終集計から除外。
  初期probeログの `NekoMuon beta=.9` 表記は診断側の表示不備で、実行はCLI factoryの
  通常Muon .95。最終4回では表示を訂正済み。

## アムダールの法則による優先順位

最終4回の同期付き診断（旧/新それぞれ10 steps）の平均:

| 区間 | 旧版 ms | 新版 ms |
|---|---:|---:|
| zero grad | 0.166 | 0.150 |
| forward + backward + reduce | 1,214.64 | 919.06 |
| clip | 1.851 | 1.838 |
| Muon | 97.39 | 95.41 |
| AdamW | 29.58 | 27.90 |
| 合計 | 1,343.63 | 1,044.37 |

旧版の90.40%がforward/backward/reduce。
`S = 1 / ((1-p) + p/s)`より、残り約9.6%だけを無限に高速化しても約1.106倍が上限。
追加同期を入れた旧版eager診断では、DRN forward 392.83 ms、DRN backward
（状態再計算を含む）628.02 msが大きかった。この診断時間を通常Graph step時間に
足し合わせてはいけない。優先箇所の選定に使用し、採用判定は上記の通常経路A/Bで行った。

## 実装

`flash_attention.cu` のDRN Tensor Core forwardにwarp単位の行分割経路を追加。

1. 旧版は1バッチを256-thread CTAで処理し、value tileを順番に計算。
   tokenごとに複数の全CTA同期とFP32 stateのglobal load/storeを行っていた。
2. 新版は1warpが16 value行を所有。行間は独立なので並列化し、再帰状態を
   FP32レジスタに保持。BF16 WMMA operandだけshared memoryへ配置する。
3. 既存と同じK tile順、Q/K列配置、BF16丸め、FP32蓄積・更新式を維持。
   全CTA同期をwarp同期へ置き換える。backwardで必要なFP32履歴は引き続き出力する。
4. K=16/32、対応するV=16の倍数に適用。その他の形状とV2/V3は従来CUDA経路を維持。
   GPU型番での分岐はない。SM80/86/89/90とPTXをbuildし、実機測定はSM86のみ。
5. backward前の状態再計算も同じforward入口を使うため、その時間も短縮。
   backward数式・atomic加算・optimizer・保存精度は変更していない。

通常Muonを受け付けるようprofilerの対象検査と表示を更新。
`build-cuda.ps1 -OutputDirectory ...` を追加し、候補DLLを本番用DLLとは別にbuild可能にした。
引数なしの既存build出力先は維持する。

## 数値検証

同じ診断プログラムを旧/新DLLで実行し、非ゼロ初期stateからの
BF16出力、全時刻のFP32状態履歴、最終FP32 stateのSHA256を比較。
**全5形状・全15ハッシュが完全一致**した。

| B / T / K / V | 旧カーネル平均ms | 新カーネル平均ms |
|---|---:|---:|
| 3 / 33 / 16 / 16 | 0.0544 | 0.0338 |
| 2 / 257 / 16 / 48 | 0.6416 | 0.1922 |
| 8 / 2048 / 32 / 32 | 5.6191 | 2.6005 |
| 2 / 65 / 32 / 128 | 0.5435 | 0.0691 |
| 2 / 33 / 48 / 32（既存fallback） | 0.1677 | 0.1735 |

単体時間は5 warmup後20回の平均、各1runであり、fallbackの小差を退行と断定しない。
hashは最初のforwardから取得。timingは連続するstate更新なので同じ入力からの
独立試行平均ではない。学習全体の採用根拠は反復したA/B測定。

学習trace全体のbit一致は主張しない。既存backwardにはFP32 atomicが残る。
最終測定stepのlossは旧6.5947 / 6.6048、新6.5995 / 6.6081。
合成固定batchのloss低下は実データ収束の証明ではない。

## 残っているもの・範囲外

- 2GPU経路の既存host staging通信は残る。測定stepあたりH2D 190,493,664 bytes、
  D2H 190,231,552 bytesで、変更前後同じ。「tokenとlossだけの転送」とは主張しない。
- backwardのQ/K atomic競合、linear/FFN等は次の改善候補。今回は変更していない。
- 210/2100-step soak、全solution回帰、長時間の実FineWeb収束比較は未実施。
- 本番JSON・tokenizer・checkpoint・metricsを編集せず、学習プロセスを停止していない。
