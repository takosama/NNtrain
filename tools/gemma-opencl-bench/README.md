# Gemma 3 Q8_0 CPU/OpenCL benchmark harness

`Invoke-GemmaOpenClBenchmark.ps1` compares the current NNtrain.Cli Gemma 3 path
with a fixed greedy prompt. It starts one process per case and records the CLI's
load, first-token, and decode measurements. It does **not** call an external
server. Running it without `-Run` only prints the proposed sequence; it does
not load the model or initialize OpenCL.

## Suggested controlled sweeps

Run these only when no other GPU benchmark or model process is active. First
compare CPU and a small OpenCL layer sweep at the same thread count:

```powershell
pwsh -NoProfile -File tools/gemma-opencl-bench/Invoke-GemmaOpenClBenchmark.ps1 -GpuLayers 0,10,20 -Threads 8 -Contexts 1024,4096 -Repetitions 2
```

Add `-Run` to execute the printed plan. After reviewing the first sweep, test
threads with the best safe GPU layer count, for example:

```powershell
pwsh -NoProfile -File tools/gemma-opencl-bench/Invoke-GemmaOpenClBenchmark.ps1 -GpuLayers 0,20 -Threads 4,8,12 -Contexts 1024,4096 -Repetitions 2 -Run
```

The GPU cases pin `GGML_OPENCL_PLATFORM=Intel` and `GGML_OPENCL_DEVICE=B580`
inside each child process, selecting the first matching B580. This sweep
measures the single-GPU route; the GUI's two-B580 default uses 43 layers and
a 53:47 split, as recorded in the latest optimization report.
`--backend cpu` is used for `-GpuLayers 0`; positive
layer counts use `--backend opencl`.

## What is held constant

- The model SHA-256 is verified once before any run. The CLI and bundled
  `ggml-opencl.dll` SHA-256 values are saved in `manifest.json`.
- Every case uses the same short prompt, maximum new-token count, greedy
  sampling (`temperature 0`, `top-k 1`), and a fresh sequential CLI process.
- Case order is shuffled reproducibly with `-Seed`; no two tests run together.
- Raw CLI output is saved as `*.stdout.log` and `*.stderr.log` for every case.
  Failed, timed-out, and short-output cases remain in `runs.csv` but are
  excluded from the median in `summary.csv`.

Configured contexts of 1024 and 4096 allocate different context capacities.
The fixed prompt is short in both, so this sweep measures capacity effects on
load and short-prompt generation. It is not a 1024-token versus 4096-token
prefill benchmark. Use a separately token-calibrated prompt for that question.

The CLI's `prefill/first-token` value includes both stages. `decode tok/s`
excludes the first token and is only valid when at least 32 tokens are
generated by default. Check `PromptTokens`, `GeneratedTokens`, and
`GraphSplits` in `runs.csv` before interpreting speed ratios. For publication,
increase `-Repetitions` and report sample variation from `summary.csv`.

Outputs are placed in a new `benchmark-results/gemma3-opencl-sweep-*`
directory for each `-Run`; existing runs are not overwritten.
